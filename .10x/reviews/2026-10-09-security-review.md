# Security review, Phase 0 (2026-10-09)

Role: Security Engineer (Prompt 3). Scope: what an attacker with a normal account (or the server itself, for the commitment) can do to Phase 0, before strangers arrive. Branch `claude/sharp-cannon-4150j6`, starting at `3e13ae8`. Nothing was run against production except two read-only public reads: `/auth/v1/settings`, and the Supabase security advisors through the MCP.

## Executive summary

1. **Found:** one High, six Medium, six Low, two Info.
   - High (SR-01): one account could flood the shared lobby. 200 junk frames reached each of 5 other players as 200 frames, and the socket was never closed.
   - Medium:
     - (SR-02) the same flood on a table socket;
     - (SR-03) a deck reveal could hide a re-dealt card and still show "Deck verified";
     - (SR-04) a short `DEV_AUTH_SECRET` let anyone sign in as anyone;
     - (SR-06) invite tables can be spammed without limit;
     - (SR-07) connection floods (one account or IP, uncached Supabase lookups);
     - (SR-08) a folded player's own cards are never verifiable.
2. **Fixed now, each red then green:** the High, three Mediums (SR-02 to SR-04) and one Low (SR-05). Mediums SR-06 to SR-08 and the other Lows are tickets, user actions or accepted risks, with file:line below.
   - Held: auth, seat integrity, frame redaction (every type, plus a byte-equality side-channel test), the database access matrix (14 tables × 4 callers × 4 operations) and the service-key destination.
3. **No Critical or High is open.** The two items marked NOT TESTABLE are dashboard checks for you: the redirect allowlist, and whether the production Worker has a `DEV_AUTH_SECRET`.

## Not tested, and why

- **Anything against production beyond two public reads.** No load, no exploit, no writes (instruction). Every EXPLOITED result above comes from a local test, a probe or reading the code.
- **The Supabase redirect allowlist and Site URL, and Worker secrets in production.** Dashboard-only; listed as your checks.
- **Timing side channels on real hardware.** Reasoned from the code, not measured.
- **Queue flooding with many real accounts, and Supabase-side rate limits.** These would need real accounts and platform behaviour.
- **Durable Object eviction under real platform pressure.** Only the local runtime's `abortAllDurableObjects` path is covered (existing restart tests).
- **The AI-coach tables' runtime path.** The `learning_cloud` tables are in the matrix, but no coach code runs on `main`.
- **Phase 1 surfaces** (ratings, grades, reports): not built yet.
